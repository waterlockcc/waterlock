Git over smart HTTP, against any host: GitHub, GitLab, Bitbucket, Gitea, Azure DevOps, or `git http-backend`. The agent runs plain `git`; the gateway reads each request, checks the repo and the refs being pushed, and adds the real credential.

```ts
import { git } from "@waterlock/gateway/providers/git";

git({ upstream: "https://github.com", credentials });

// several hosts: one provider each, named `<host>-git`; the session token picks the host
git({ id: "github-git", upstream: "https://github.com", credentials: githubToken });
git({ id: "gitlab-git", upstream: "https://gitlab.com", credentials: gitlabToken });
git({ id: "forge-git", upstream: "https://git.example.com/gitea", credentials: forgeToken });
```

Upstream gets `Authorization: Basic <username>:<token>`. `username` defaults to `x-access-token`:

| Host | `username` |
|---|---|
| GitHub (PAT or app installation token) | default |
| GitLab, Azure DevOps (PAT) | default (any username works) |
| Bitbucket Cloud (access token) | `x-token-auth` |
| Gitea, Forgejo | your username |

`r.params.repo` is the path as the agent sent it. GitHub and GitLab resolve `Acme/App` and `acme/app` to the same repo, so compare it lowercased: `r.params.repo.toLowerCase() === "acme/app"`. Compared as-is, an allow rule refuses `Acme/App`, and a deny rule lets it through.

## How git talks to the gateway

Every `git` command that talks to a remote makes two kinds of HTTP request, and each one is checked on its own:

1. **Advertise.** git asks which branches and tags the repo has (`GET <repo>/info/refs`). Nothing is changed or downloaded yet.
2. **RPC.** git does the work in a `POST` (a fetch may send several). On a fetch, it names the commits it wants and the server sends them. On a push, it lists each ref to change (`refs/heads/agent/fix`: old commit to new commit), then uploads the new commits.

| Command | Requests | Action |
|---|---|---|
| `git clone`, `fetch`, `pull`, `ls-remote` | advertise, then RPC | `git.fetch` |
| `git push` | advertise, then RPC | `git.push` |

A ref is the full name of a branch or tag: branch `main` is `refs/heads/main`, tag `v1` is `refs/tags/v1`. Only the push RPC says which refs change, so ref rules check `r.context.phase === "rpc"`. A fetch can't be limited by branch: an agent that can read a repo can read all of it.

## Actions

| Request | Action | `r.context` |
|---|---|---|
| `GET <repo>/info/refs?service=git-upload-pack` | `git.fetch` | `{ phase: "advertise" }` |
| `POST <repo>/git-upload-pack` | `git.fetch` | `{ phase: "rpc" }` |
| `GET <repo>/info/refs?service=git-receive-pack` | `git.push` | `{ phase: "advertise" }` |
| `POST <repo>/git-receive-pack` | `git.push` | `{ phase: "rpc", updates, push_options }` |

- `r.params.repo`: the path on the host without `.git`, case kept, e.g. `acme/app`, `group/sub/project`, `org/project/_git/repo`.
- `updates`: one entry per ref, `{ ref, old, new, kind }`. `ref` is the full name (`refs/heads/main`, `refs/tags/v1`); `kind` is `create`, `update` or `delete`.
- `push_options`: the `git push -o` values. Some hosts act on them (GitLab's `ci.skip`, `merge_request.create`).
- Every push starts with the `advertise` request. Denying it stops the push before any objects are sent, which is how a read-only agent fails fast. A rule that allows pushes must allow both phases; narrow on `r.context.phase === "rpc"` to read `updates`.
- Dumb HTTP, LFS and signed pushes are refused.

```ts
policy: [
  // read and push acme/app
  { when: (r) => r.params.repo.toLowerCase() === "acme/app" },
  // only to agent/* branches
  {
    when: (r) =>
      r.action === "git.push" &&
      r.context.phase === "rpc" &&
      r.context.updates.some((u) => !u.ref.startsWith("refs/heads/agent/")),
    action: "deny",
    reason: "Agents push only to agent/* branches.",
  },
  // never delete
  {
    when: (r) =>
      r.action === "git.push" &&
      r.context.phase === "rpc" &&
      r.context.updates.some((u) => u.kind === "delete"),
    action: "deny",
    reason: "No deleting branches.",
  },
]
```

The gateway reads the push commands, not the pack: it can't tell a force push from a fast-forward, and doesn't see file contents. Use the host for those (GitHub rulesets, GitLab protected branches), and a token without permission to change CI workflow files.

## Harness

The agent uses plain `git` with the gateway as the remote. Send the session token as a header, or as the password of Basic auth (e.g. from a credential helper):

```sh
git -c http.extraHeader="Authorization: Bearer $SESSION_TOKEN" clone http://127.0.0.1:8787/acme/app.git
git clone http://agent:$SESSION_TOKEN@127.0.0.1:8787/acme/app.git
```

Set `GIT_TERMINAL_PROMPT=0` so git fails instead of waiting for a password. Give the agent no SSH keys: SSH doesn't go through the gateway. To keep existing remote URLs, rewrite them with `git config url."http://127.0.0.1:8787/".insteadOf "https://github.com/"`.

## Errors

Git shows the gateway's reason in its own output. A denied fetch, or a denied push before any objects are sent:

```
remote: Error for waterlock proxy: no allow rule matched
fatal: unable to access 'http://127.0.0.1:8787/acme/secret.git/': The requested URL returned error: 403
```

A denied push, per ref:

```
 ! [remote rejected] HEAD -> main (Error for waterlock proxy: Agents push only to agent/* branches.)
error: failed to push some refs to 'http://127.0.0.1:8787/acme/app.git'
```

One denied ref rejects the whole push. Errors before the push commands are read are plain text with the gateway's [status and code](/docs/concepts/request-flow#errors); a 401 on a git path also carries a `WWW-Authenticate: Basic` challenge, so git sends Basic credentials.
